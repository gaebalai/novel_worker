
# 설계 사고방식: Opus(Claude Code)라서 진행된 것인가, 고정 흐름으로 만들 수 있는가

- 날짜: 2026-10-03
- 재료: novel-tools의 검증 기록·아이디어 씨앗·그라우발 제6회의 제작 메모·공개 엔지니어링 정리, 70커밋(`Novel_1`~`Series_Grauwall/Grauwall_06`)
- 결론부터: **①과 ② 중 하나가 아니라, 일의 층에 따라 갈린다.** 작품을 만드는 흐름은 ②(고정 흐름)로 만들 수 있었고, v1.0에서 앱으로 만들었다. 고정할 수 없는 나머지(도구 개수와, BRIEF를 쓰는 창작력)가 ①(다른 하네스 × 모델)로 정말 시험해야 할 부분이며, 그것을 위한 시험을 만들었다.

---

## 1. 질문 다시 세우기

‘Claude Code의 Opus 5.5라서 매끄럽게 진행됐다’는 맞다. 다만 Opus가 무엇을 하고 있었는지 나눠 보면 하네스의 힘과 모델의 힘이 섞여 있다.

제6회 『백탑의 사자』의 실적(제작 메모 2-1): 상위 모델(Claude)이 들어간 것은 **설계 수정 2번·장 손질 5번·교정 1번**. 나머지 약 90번의 호출은 싼 모델(haiku-5.5와 luna-pro). 비용은 1달러 단위에도 못 미친다.

한편, 기록에 남지 않은 Opus의 일이 있다.

| Opus가 하던 일 | 기록에서 보이는 모습 | 종류 |
|---|---|---|
| BRIEF(제6회는 53,493자)를 쓴다 | ‘Claude가 BRIEF를 작성’ | **모델의 창작력** |
| 작품마다 CANON 템플릿·LEDGER 항목·프롬프트를 손으로 맞춘다 | `templates/`와 `prompts/`가 작품마다 다름(제6회는 ‘엘노’ ‘백탑’ 포함) | **손으로 맞추기**(기계화 가능) |
| `config.json`의 `slot_plan`을 BRIEF의 배치표와 손으로 맞춘다 | `_comment_series`: ‘slot_plan은 BRIEF.md 제4-2절과 반드시 동시에 변경한다’ | **손으로 맞추기**(기계화 가능) |
| CANON 심사가 수렴하지 않을 때 전체를 훑어 고친다 | ‘haiku와 luna의 왕복이 수렴하지 않아서 Claude가 2번 전체를 훑어 고쳤다’ | **모델의 힘**(API 호출 한 번으로 만들 수 있음) |
| 통과하지 못한 장을 지적 부분만 고친다 | 제4·6·14·16·20장 | 위와 같음 |
| 전문 교정(22건)을 `proofread_apply.py`의 Python 리스트로 쓴다 | `EDITS = [...]`가 코드 안에 있음 | 위와 같음(JSON으로 하면 기계화 가능) |
| 추론 폭주·마감·패킷 불일치를 로그로 진단해 코드를 고친다 | 제6회에서만 novelctl 개수 10건 | **하네스 × 모델의 힘**(고정 불가) |
| 실험 설계와 분석(evolve·mask·compe) | Novel_4 | 위와 같음 |

즉 Opus에 대한 의존은 네 종류로 나뉜다.

## 2. 층별 판단

| 층 | 내용 | 고정 흐름화(②) | 다른 하네스(①) | v1.0에서의 처리 |
|---|---|---|---|---|
| A. 상류 창작 | 테마 → 기획 → 분류 → BRIEF | **가능**. BRIEF를 JSON으로 내게 하고 BRIEF.md·config·CANON 템플릿을 기계로 그려 내면 손으로 맞추기가 사라진다 | 도구를 순서대로 돌리는 것은 쉽다. BRIEF를 직접 쓰는 것은 모델에 달렸다 | `studio/`(앱)와 `engine/tools/scaffold.py` |
| B. 진행 | CANON → 장 → 대장 → 최종 심사 | **이미 되어 있었다**(novelctl) | 약한 하네스도 가능(멈춰야 할 곳에서 멈출 수 있다면) | `engine/`(Grauwall_06 최신판을 범용화) |
| C. 예외 처리 | CANON 전체 수정·장 손질·교정 | **가능**. 하네스가 아니라 상위 모델을 API로 한 번 부르는 공정으로 만든다 | ‘부를지 말지’의 판단만 남는다(사람의 허가) | `novelctl rescue canon` / `rescue chapter N` / `proofread`(역할 `premium`) |
| D. 도구 개수 | 로그로 진단하고 코드 수정 | **불가능**(매번 다름) | **여기가 진짜 검증 대상** | `harness/exams/`의 L4 |

②로 만들 수 있었던 이유는 Novel_4 이후 쌓은 지식이 그대로 설계 규칙이 되어 있었기 때문이다.

- 합의는 이상치를 낳지 않는다 → 분류는 좋고 나쁨이 아니라 ‘정형에 얼마나 쏠렸는지’를 보여 주고, 이상치를 줍는 것은 사람. 이상치를 늘리는 것은 ‘수렴한 골격을 피해서’ 재제출(롤링).
- 중복 판정은 LLM에 맡기지 않는다(심판의 자기 일치 ARI 0.115~1.0) → 골격 추출만 모델에 맡기고 가까운 정도는 도구가 센다.
- 품질의 천장은 작가가 정한다 / 싼 모델은 전체 정합성을 맞추며 고치는 데 서툴다 → 쓰기·대조는 싼 모델로 몇 번이고, 전체 정합성은 상위 모델로 한 번만.
- AI의 보고는 곧이곧대로 믿을 수 없다(dsp·lc: 78%) → 교정안은 ‘원문이 원고에 딱 한 곳만 있는’ 것만 통과시킨다. 하네스 시험은 보고가 아니라 디스크 상태로 채점한다.
- 같은 사실이 두 곳에 쓰여 있으면 반드시 어긋난다 / 쓰여 있지 않은 세계의 전제는 싼 모델이 현대의 상식으로 메운다 → CANON 템플릿에 ‘세계의 전제(적용 범위 포함)’ 절을 필수로 했다.

## 4. 아직 모르는 것 (솔직하게)

- **진짜 모델로는 한 번도 돌려 보지 않았다.** 모두 가짜 모델로 확인한 것. 첫 실전에서는 제안·골격·BRIEF의 JSON을 각 모델이 서식대로 돌려주는지, BRIEF의 질이 손으로 쓴 5만 자에 얼마나 다가가는지를 봐야 한다.
- **상위 모델의 OpenRouter 이름**을 `anthropic/claude-opus-5.5`로 임시로 두었다. 다르면 `config.default.json`과 studio 설정에서 고친다. Novel_5에서는 ‘Opus는 OpenRouter를 거치면 비싸니까 agy로’라는 판단이 있었다. studio의 상위 모델 역할을 agy에 잇는 접속부는 v1.0에 들어 있지 않다(issue로 만들었다).
- **BRIEF의 JSON은 손으로 쓴 BRIEF보다 얇다.** 제6회 BRIEF에 있던 ‘프로듀서 확인 사항’ ‘긴 실의 배치’ ‘시리즈의 규율’은 범용 항목으로는 나타낼 수 없다. 시리즈물은 당분간 손으로 쓴 BRIEF + 지금의 Grauwall 흐름이 낫다.
- **분류 문턱값(0.5)은 가짜 모델로만 맞췄다.** 진짜 안으로 사람의 ‘비슷하다’와 도구의 ‘비슷하다’가 맞는지 확인한다.
- 작품 폴더에 도구를 복제하는 방식은 바꾸지 않았다(보호 파일 지문 구조를 깨지 않기 위해). 패키지화는 issue로 만들었다.

## 6. 새 발상의 씨앗 (이 정리에서 나온 것)

1. **‘상위 모델 의존도’ 진단.** 업무 흐름을 싼 모델로 돌렸을 때 ‘어디서 멈추고, 상위 모델 한 번으로 통과하는가’를 세면 그 업무의 상위 모델 의존도가 나온다. 제6회는 8/98. AIOps 운영 설계에서 ‘어느 공정에 비싼 모델의 예산을 둘지’를 정하는 근거가 된다. `rescues` 수가 그대로 KPI.
2. **하네스 성실성 벤치.** L1·L2는 똑똑함이 아니라 멈추기·허가 지키기·확인한 것만 보고하기를 잰다. 보고가 아니라 디스크 상태로 채점하는 방식은 업무 에이전트 채용 시험으로 소설 밖에서도 쓸 수 있다(티켓 대응, 변경 관리, 장애 1차 대응으로 바꾸기만 하면 됨). ‘업무 AI에 필요한 것은 성실함’을 숫자로 만드는 도구.
3. **사양서 lint.** BRIEF를 JSON으로 만들어 기계 검사했더니 ‘회수가 설치보다 앞섬’ ‘장 수 불일치’ 같은 구조 오류가 쓰기 전에 사라졌다. 기획서·요건 정의·변경 신청도 같은 식으로 ‘구조만은 기계가 확인하고, 내용은 사람과 모델이 쓴다’ 형태로 만들 수 있다. 대장(작성 → 변경은 승인 필요 → 반영 → 재고 조사) 사고방식과 그대로 겹친다.
4. **기획 분류를 사내 미래 계획에.** studio의 ‘제안 → 골격 추출 → 규칙으로 분류 → 수렴을 피해서 재제출’은 소설 고유 부분이 prompts/와 similarity.py의 항목뿐이다. base_url은 OpenAI 호환이면 바꿔 끼울 수 있으므로 사내 model router(익명화 포함)로 향하게 하면 반년 이후의 계획 수립에 그대로 쓸 수 있다. 골격 항목을 ‘누가 곤란한가·무엇이 바뀌는가·무엇이 전제인가·무엇이 뒤집히는가’로 바꾸면 사업안이 정형으로 수렴하는 모습이 보인다.
5. **이상치 예언 대장.** 분류에서 ‘이상치’가 된 안을 날짜와 함께 대장에 남기고, 반년~1년 뒤에 ‘맞았는가’를 대조한다. 가설을 세우고 시간이 지난 뒤 확인하는 도구. 이상치는 합의에서는 생기지 않고 사람이 주울 수밖에 없다──그렇기에 주운 이상치의 적중 기록은 그 사람의 안목 기록이 된다.
6. **‘고정할 수 없는 층’을 상품으로 삼지 않는 설계.** 도구 개수(D층)만은 매번 다르다. 이것을 사람 + 최상위 모델의 일로 명시하고 나머지를 고정 흐름으로 떨어뜨리면, 운영 비용을 ‘고정 부분 × 횟수 + 예외 × 단가’로 견적 낼 수 있다. 수탁 견적이나 구독 가격 설계의 틀이 된다.
